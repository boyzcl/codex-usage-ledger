# 部署与恢复

更新程序与纠正旧账本分开执行。先完成备份和离线修复验收，再切换程序与数据库。普通功能要求 Node.js 22.13+，修复在 Node.js 22 系列中要求至少 22.16.0 且提供原生 SQLite backup API。

1. 记录旧提交、运行时、程序路径、启动项、配置和数据库聚合。保留含已提交 WAL 事务的 SQLite 一致性备份、旧构建、配置与启动项副本。检查磁盘空间。
2. 在独立目录检查新版本的类型、lint、构建和回归。准备具体恢复命令；私人数据与机器路径不进入 Git。
3. 停止监控并确认旧进程退出、账本无其他写入者。此后获取最终一致性备份；不得用早先的预览覆盖最新账本。
4. 以最终备份运行 `repair-preview`。源仍可增长；读取中变化的文件会延后，恢复后须重试并记录。核对全部原始 Token 事实、历史价格引用、额度与账户观测保全，并区分修复变化与新采集。
5. 更新既有程序目录并构建。旧代码不得访问新 schema。关闭数据库连接，检查事务和一致性；处理旧 WAL/SHM 后，从已验证的新副本切换账本。不得把旧 WAL 留给新数据库。
6. 恢复服务，核对实际 PID、启动时间、命令与构建路径、心跳、本地同步和官方额度采集。验证全局 CLI 与登录自启动，记录中断起止时间。监控停止期间没有连续官方采样；本地日志补读不等于恢复了缺失的官方快照。
7. 检查发布内容无私人数据或秘密，确认远端没有冲突后正常推送。生产 HEAD、公开远端 SHA 与发布版本须一致。

切换前失败时保留失败副本并恢复旧服务。切换后失败时，先停新服务并确认所有写入者退出，保存失败现场，再从最终旧备份恢复到新路径；同时恢复旧代码、旧构建和必要配置后重新启动。保留新版本运行后的增量，旧代码恢复后从源补读。不要直接覆盖打开的数据库，不要删除源日志，也不要无故回滚已经验证成功的部署。

待核对事实不是零，也不等于已证实的重复消耗。部署成功不代表全部历史归属已核实或套餐容量已可靠推断。
