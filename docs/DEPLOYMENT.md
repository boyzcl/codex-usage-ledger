# 部署与恢复

更新程序与纠正旧账本分开执行。先完成备份和独立副本验收，再切换程序与数据库；需要历史纠正时才运行修复。普通功能要求 Node.js 22.13+，修复在 Node.js 22 系列中要求至少 22.16.0 且提供原生 SQLite backup API。

1. 记录旧提交、运行时、程序路径、启动项、配置和数据库聚合。保留含已提交 WAL 事务的 SQLite 一致性备份、旧构建、配置与启动项副本。检查磁盘空间。
2. 在独立目录检查新版本的类型、lint、构建和回归。准备具体恢复命令；私人数据与机器路径不进入 Git。
3. 停止监控并确认旧进程退出、账本无其他写入者。此后获取最终一致性备份；不得用早先的预览覆盖最新账本。
4. 以最终备份创建独立副本并验收。v0.4.5 从已验收的 v0.4.4 升级只增建 `valuation_runs`、`valuation_results` 和结果索引，无需 `repair-preview` 或重扫源日志。逐主键核对所有原表列及 raw、旧价格、入账金额/引用、额度/账户/observations 和派生历史均保全。在另一私有验证副本上测试明确标为合成的后继导入、事件回算、指定时刻重估、重复幂等及成对导出；合成规则不能进入部署副本。需要历史纠正时另运行 `repair-preview`，变化源延后重试，区分修复变化与新采集。
5. 更新既有程序目录并构建。旧代码不得访问新 schema。关闭数据库连接，检查事务和一致性；处理旧 WAL/SHM 后，从已验证的新副本切换账本。不得把旧 WAL 留给新数据库。
6. 恢复服务，核对实际 PID、启动时间、命令与构建路径、心跳、本地同步和官方额度采集。验证全局 CLI 与登录自启动，记录中断起止时间。监控停止期间没有连续官方采样；本地日志补读不等于恢复了缺失的官方快照。
7. 先完成部署验收，再按已获授权检查发布内容无私人数据或秘密、确认远端没有冲突并正常推送。生产 HEAD、公开远端 SHA 与发布版本须一致；预览或提交本身不授权上线和推送。

切换前失败时保留失败副本并恢复旧服务。切换后失败时，先停新服务并确认所有写入者退出，保存一致失败现场、代码、配置及全部新增事实。没有上线后写入时可以从最终旧备份恢复到新路径，同时恢复旧代码、构建和配置。已经产生增量时，不得用旧备份覆盖最新库；源补读不能恢复新增官方观测、手工价格或重算历史。优先保留最新库并修复当前代码；回退需在副本对账并给出增量保全方案。不要覆盖打开的数据库，不要删除源日志，也不要无故回滚已验证成功的部署。

## v0.4.5 的目录兼容边界

部署验证必须使用最新停服一致备份，早先冻结预览仅作证据。新表与旧表并存，原事实不作历史重计价；生产默认56条种子价格没有新官方调价时继续原样保存。调价和回算通过 [使用指南](USAGE.md) 中的显式命令执行，不作为升级的自动步骤。

v0.4.4 不理解 `supersedes`。尚未导入新后继时，旧构建可读取原表，但回退仍须保留两个新表。已经导入后继时，代码直接回退会把旧开放规则和新后继视为未声明重叠，新入账或重估金额可能未知。旧入账引用仍保留，但不能把这种回退解释为正常计价。不要删除新价格、修改旧截止、抹掉重算表来迁就旧程序。此时优先回退有问题的具体代码变更并保留 C 的目录解释；若只能启用 B，则暂停自动写入，在保存最新现场的副本上以只读 SQLite 核对旧事实，等待兼容修复后再恢复采集。发布撤回使用普通 revert，不强推。

待核对事实不是零，也不等于已证实的重复消耗。部署成功不代表全部历史归属已核实或套餐容量已可靠推断。
